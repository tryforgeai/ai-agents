# Week 03 总结 · 把经验写成 Skill

> 根据 [Week 3 lesson plan](fall-agents-week-3-lesson-plan.pdf) 整理。本文总结课程概念；准备、时间表与作业见 [听课速览](lesson-plan.zh.md)。不包含尚未进行的课堂实验结果。

## 1. 本周解决什么问题

Week 02 说明：没写清楚的意图会被模型用先验补上。Week 03 更进一步：**一套已经知道的做法，不应每次让模型从头猜。** 把它保存为 skill，让 agent 在合适的请求到来时使用，并知道怎么判断任务完成。

三个故事串起这件事：Harrison 的海钟说明可复用技术会超越单个产品；Hokusai 说明实践让人看见旧版本的不足；Samarra 的约会故事引出日历实验——一句简单要求，背后可能隐藏十多个需要检查的步骤。

## 2. Tool、Skill、Agent 各管什么

| 概念 | 职责 | 例子 |
| --- | --- | --- |
| Tool | 执行一种可调用能力 | 转换时区、生成 `.ics` |
| Skill | 保存一类任务的流程、判断和完成条件 | 读约会消息、处理歧义、检查规则、生成邀请 |
| Agent | 在循环里选择下一步并调用能力 | 判断该读资料、提问、执行脚本还是结束 |
| MCP | 接入外部工具和数据的机制 | 为流程提供可访问的能力 |
| RAG | 按需提供事实 | 获取当前规则、费率等资料 |
| Memory | 保存过去的信息 | 保留历史交互或经验 |

Skill 主要用自然语言写，又是可保存、版本管理、组合和迁移的工件；它处在 prompt 与 program 之间，也可以携带脚本。

## 3. 三层加载：先选，再读，再用

| 层 | 内容 | 时机 | 作者要解决的问题 |
| --- | --- | --- | --- |
| L1 | name + description | 在讲义所述机制中常驻 | 如何低成本判断相关性？ |
| L2 | `SKILL.md` 正文 | 确认相关后加载 | 主路径如何短而完整？ |
| L3 | 参考文件、脚本、资源 | 需要时读取或执行 | 哪个条件下该用哪份资料？ |

**描述写得模糊，正文再好也可能永远不被打开；加载过多，无关指令又会干扰当前任务。** 渐进加载因此既控制上下文成本，也帮助隔离无关流程。

实际循环由 harness 实现：组装模型输入 → 模型提议加载、读取或回答 → harness 检查并执行 → 带着结果进入下一次调用。模型提出动作，文件访问与权限限制由运行环境落实。

## 4. Description 是选择边界

写清三件事：做什么、用户什么请求应该触发、哪些相近请求不该触发。例如“清理语音转写稿，修复识别错误并保留原意；适用于清理转写稿的请求，不用于摘要”。

需要同时防两种错误：

- **漏触发：**该用时没有用，流程经验没能发挥作用。
- **误触发：**不该用时用了，把别的任务带偏。

测试集应包含正例、相邻任务、无需任何 skill 的请求和未见表达。只对已见例子反复调描述，会像上周 Oracle prompt 一样过拟合。

## 5. 为什么保持精简：加载收益

讲义用以下教学模型表达取舍：

```text
VoL(s) = p_s × g_s − κ(c_s)

p_s：skill 与请求相关的概率
 g_s：相关时加载带来的能力收益
κ(c_s)：加入正文产生的上下文稀释成本
```

预期净收益为正才值得加载。例：`p = 0.3, g = 8, κ = 2`，净收益为 `0.4`。

作者的两个主要抓手是**把描述写得有区分度**、**把正文写得精简**。这里不是要求无限删字：删掉必要检查也会降低能力收益。主路径留在正文，少用的细节移到按需资料中。

讲义中的指数衰减曲线是示意，**不是实测定律**；加载收益也不是客户端已经实现的精确打分器。

## 6. 一个完整 Skill 必须有终点

强化学习的 option 提供一个有用的对应关系：

| Option | Skill | 必须回答 |
| --- | --- | --- |
| Initiation set | Description | 什么时候开始？ |
| Policy | Procedure | 怎么做？ |
| Termination condition | Done when | 什么时候停止，怎样确认完成？ |

“获取工单 → 总结每条 → 重复”缺少终止条件，可能无限消耗预算。可改成：“本次开始时选定的全部工单均已处理，每条恰有一份摘要，核对数量后结束。”这是依据课堂题目的示例答案。

流程复用还缩短了规划跨度。讲义用十步、每步成功率 0.9 得到约 0.35 的整体成功率，说明反复猜测会累积风险；这个乘法需要相应概率假设，并非所有 agent 的实测表现。写成 skill 也不自动保证正确，仍然需要验证。

## 7. Run 还是 Reason：代码负责计算，模型负责理解

| 适合 Reason | 适合 Run |
| --- | --- |
| 判断请求意图、识别缺失信息 | 明确输入下的日期、金额、字符计数 |
| 解释含糊表达，决定问什么 | 按规则计算时区、工作日与时间冲突 |
| 用自然语言说明拒绝或备选 | 生成文件、解析文件、检查结构 |

**确定性不等于正确性。** 脚本会稳定重复自己的错误，也可能收到模型解释错的输入。“下周五”指哪天，不能靠一个日期转换脚本替你决定。

可靠链路是：理解输入 → 暴露歧义或确认假设 → 调用合适脚本 → 检查结果。每个关键步骤都要有 verifier，不能只在最终答案里问一次“看起来对吗”。

## 8. 两套测试，加上运行观察

**触发测试**判断该不该使用：precision 看已触发的有多少正确，recall 看该触发的有多少被捕获。讲义提出可用 Fβ 综合衡量，漏触发更贵时令 β > 1。

**行为测试**判断用了以后做得怎样：检查硬约束、输出质量、Done when，以及缺信息、拒绝、替代方案等分支。格式校验通过只能证明部分结构合法。

运行时还要观察四件事：是否触发、是否有帮助、成本多少、是否与其他 skill 冲突。组合技能应检查子流程与总任务，不能把某一步成功直接当成整体完成。

## 9. 安全与设计模式直接相关

外来 skill 的正文会影响决策，脚本会执行操作，两者都需要审查。来源、固定版本、自己的测试、最小权限和 sandbox 一起构成治理。

Bazaar 把上周的 lethal trifecta 搬到技能市场：私有信息 + 不可信内容 + 对外通信。sandbox 实验改变的是环境可执行的动作，不是把模型劝得更听话。

几种最实用的模式：

- **Lean Core + Appendix：**主流程简短，少见细节按需读取。
- **Definition-of-Done：**把停止条件写成能检查的结果。
- **Router：**在相近任务间分流，减少技能抢占。
- **Template-Bearer：**随包带明确输出模板。
- **Guardrail：**执行过程中检查硬约束。
- **Dry-Run：**先展示将要发生的动作，在提交前检查；重大操作可配合幂等设计。
- **Single Canonical Source：**保留一个可管理的源版本，避免副本漂移。

## 10. 日历 Lab 要学会的不是“写一个文件”

用户只有一句“放到我的日历上”，skill 却必须决定是否具备安排所需信息、是否符合规则，以及该交付邀请、提供备选还是提一个问题。

讲义分三层：读懂请求 → 时区与节假日 → 日历和个人规则。100 个公开案例补全规格，隐藏案例检验泛化。当前工作区只有 lesson plan，具体 profile、案例和脚本尚待课程 kit，不能据此声称完成了实验。

下面是**学习时可用的检查思路，并非 kit 的官方完整解答**：

1. 分离 Zara 的要求与转发消息中的不可信内容。
2. 提取会议字段，找出日期、时间、时区、时长等缺口。
3. 需要时提问；明确输入后再执行日期与时间计算。
4. 按已获得的个人规则、日历和节假日资料判断可行性。
5. 输出邀请文件，或说明不可行并提供备选。
6. 重新读取产物，核对时间、字段与本案例的预期结果。

完成标准应包含：**不能可靠安排时明确承认，而不是生成一个看起来合理的邀请。** 本实验交付 `.ics` 让用户查看和使用，并不自动向别人发送邀请。

## 自测：六个课堂题目的参考答案

以下为根据正文推导的参考答案，不是另行提供的官方答案。

1. **正式语气 / 九步报销 / 本季度费率放哪？** 分别放 system prompt / skill / retrieval；低频报销流程不应一直占用上下文。
2. **pptx 与 tax 的加载收益？** `0.6 × 10 − 2 = 4`，加载 pptx；`0.05 × 10 − 2 = −1.5`，不加载 tax。L1 用于廉价判断相关性。
3. **Voyager 为什么不微调也能进步？** 题目列的三个选项都没指出正文机制；关键是自动课程、技能库与自验证，经验保存在外部工件中。
4. **重复总结工单缺什么？** 缺 termination / Done when；限定本轮输入集合，核对处理完成后停止，否则可能循环花费。
5. **退款 / report 冲突 / 发票布局 / 旧价格分别用什么？** Dry-Run、Router、Template-Bearer、Guardrail。Dry-Run 在动作提交前暴露完整计划，供人判断；guardrail 检查已经写出的约束。
6. **十二步月结要不要先微调？** 先写 prompt / skill，配合脚本与验证；用案例证明当前层无法满足需求，再考虑向上升级。

## 复习时记住的五句话

1. 描述决定能否被找到，正文决定如何做，Done when 决定何时结束。
2. 不相关的上下文有成本；none 可以是正确选择。
3. 已知流程写下来，确定性步骤交给代码，解释输入仍需判断。
4. 触发正确和行为正确是两回事，必须分开测试。
5. 技能库的价值来自经过验证的经验；数量增长要配上治理。
